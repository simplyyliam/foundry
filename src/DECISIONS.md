# Frontend decisions

Append one line per decision that isn't obvious from the code. Newest at the bottom.

- Backend contract: `appInfo()` is called on mount in `App.tsx`. `app:ready` is best-effort (it can fire before the webview listens), so don't rely on it.
- Projects: a project row in the sidebar only expands and collapses its sub-items; it doesn't navigate. The sub-items are `PROJECT_SECTIONS` in `src/features/projects/model/project.ts` (Idea → `/projects/:id/idea`, which renders the `Document` widget; Blueprint → `/projects/:id/blueprints`, still a placeholder). `/projects/:id` redirects to the first section. To add a sub-page, add an entry there and a page at `src/pages/app/projects/[projectId]/<segment>/page.tsx`.
- Archiving the open project closes it: the frontend navigates to Home itself after `archiveProject` succeeds. If the backend returns `session_running` (or any error), show its message and do nothing else.
- Delete exists only for archived projects and requires typing the project name. `deleteRepository` moves the folder to the Recycle Bin. It's the one project mutation that doesn't refresh the list itself: the dialog refreshes after its close animation, because the row (and the dialog inside it) would otherwise vanish mid-animation.
- Add-project dialog: a folder that belongs to an archived project is offered as "Archived · restore", and picking it unarchives and opens it.
- Folder picking is a custom in-app browser (`listFolders` / `folderLocations`), not the native OS dialog: the native one can't be styled. Prefer styleable in-app UI over native dialogs.
- Add-project dialog is one view: a search field, a folder button that picks where projects live (remembered in localStorage `foundry:projects-folder`), and that folder's subfolders listed below with no background. Typing a name that matches no folder offers "Create “name”" at the top. An earlier two-option design ("New repository" / "Link existing folder") was rejected; don't bring it back.
- No client-side project-name validation: `createRepository`'s own rules and messages apply (it answers `invalid_input` / `folder_exists`).
- Dialogs use the shadcn `Dialog` (`src/components/ui/dialog.tsx`), not a custom modal. Its overlay is `fixed inset-0`, so it also tints the transparent margin around the frameless window. That's known and left as is for now.
- Sidebar look (from the design): project rows and sub-items use 12px text; sub-items are a colored dot plus label with no guide line; the "Archived" group sits above "Projects", is collapsed by default and shows its count in a shadcn `Badge`. The Projects "+" is hidden until the Projects header row (only that row) is hovered or focused; the chevron then slides left to make room.
- Older code that predates the shadcn/theme-token rule: plain `<button>`/`<input>` in the add-project dialog, `ProjectNameEditor` and `ProjectsGroup`; hardcoded colors for the sidebar logo square (`bg-red-400`), the sub-item dots (`PROJECT_SECTIONS`) and the roadmap boxes (`bg-black/[0.055]`).
- Contextual panel: views come only from the route. Idea and Blueprints → Roadmap; `/teams` → Agent Chats (now `/teams/:projectId` only, see Teams routing below); `/tickets` → a reserved "tickets" view (`component: null` until the ticket system exists); Home → no panel yet (undecided). A manual dropdown switcher was built and then removed: one project's Roadmap from Teams, or Agent Chats from a project page, got messy. On routes with no view the panel unmounts (no slide animation).
- Roadmap avatar: the Product Lead's avatar can't be displayed yet. The asset protocol scope is empty and built-in avatars have no images, so it falls back to `/pfp.png` (also for no team, no Product Lead, or an error). A backend fix is coming separately.
- Roadmap generation state lives in a store keyed by project id (`features/roadmap/hooks/useGeneration.ts`), and `roadmap:progress` is listened to from app start (`AppLayout`), so switching views or pages mid-run doesn't lose it. After a full reload a run is only seen again at its next stage event; Generate meanwhile returns `generation_running`, shown as-is. The elapsed time counts up locally from the last event's `elapsedMs`.
- Roadmap load: after `generateRoadmap` succeeds, the plan is re-read and that fresh revision goes to `loadRoadmap`, instead of the revision from the click. That way an edit during a minutes-long run doesn't force another paid generation. If more requirements got confirmed during the run than the user agreed to discard, ask again with the new count before loading.
- Roadmap highlighting of uncovered paragraphs in the editor is deferred until a document editor exists. `features/document` is still empty; the "Needs a look" box lists the uncovered paragraphs meanwhile.
- Document editor: TipTap 3 with the official `@tiptap/markdown` (not the older community `tiptap-markdown`). The editor loads markdown and saves markdown; nothing else is stored. `@tiptap/pm` is listed explicitly because it's TipTap's required peer and the highlight plugin imports it. Underline is turned off (markdown can't hold it), links don't open on click (it would navigate the webview), and a bare `example.org` typed in the link field becomes `https://example.org`.
- Document saving keeps untouched blocks byte for byte (`features/document/lib/markdown-source.ts`): each top-level block is tied to its source text, verified by parsing that text alone and comparing (`eq`). A block that is the same node, or equal to a block from the loaded file (Enter at a paragraph's end, undo), is copied from the source; only edited blocks go through the serializer, which would otherwise rewrite the whole file (`_a_` → `*a*`, `\[x\]`, `&lt;`). Line endings (CRLF) are kept. Empty paragraphs are never written.
- Document autosave: 800 ms after the last edit, plus on blur, unmount (leaving the page or switching project; the widget is keyed by project) and window close. Saves run one at a time in order, and a load waits for every queued save, so the old project's edit lands before the new project loads. A save whose text equals what's on disk (or already queued) is skipped, so opening without editing never writes. Text whose save failed is kept in memory per project and shown again (and retried) on the next visit.
- Window close: the capabilities don't grant `core:window:allow-destroy`, so Tauri's `onCloseRequested` helper (which calls `destroy()`) would leave the window stuck. The document prevents the close, saves, removes its listener and calls `close()` again. If that save fails, the window stays open once with the error showing; closing again closes.
- The save status ("Saving…", "Saved", or the backend's message as-is) sits in the document's own sticky header row at the top right, not in the breadcrumb header. Nothing shows until the first edit.
- Uncovered-paragraph highlighting (supersedes the "deferred" note above): `features/document` reads `getRoadmap` itself and refetches on `roadmap:progress` `done`. A top-level block is highlighted only when its saved text, whitespace-normalized like the backend's `normalize_ws`, equals an uncovered paragraph and it hasn't been edited since; it's a ProseMirror node decoration, so the document never changes. A backend paragraph spanning several blocks (no blank line between them) is never highlighted.
- Known parser limit: `@tiptap/markdown` drops inline HTML (`a <div> tag` shows as `a  tag`). Untouched paragraphs keep it in the file; editing that paragraph removes the tag from the saved text.
- Known gap: the Roadmap panel reads `getDocument` for "No brain dump yet" only when it mounts. There's no document-changed event, so after typing the first text it keeps saying the brain dump is empty until it remounts. Not worked around (it needs a backend event, or another rule).
- Context menu: one app-wide shadcn `ContextMenu` (`AppContextMenu` in `@/shared`, mounted in `App.tsx`) replaces the webview's native menu everywhere, portals included. Its items are built at right-click time from what was clicked: groups registered with `useContextMenu(ref, provider)` (innermost region first), then built-in Undo/Redo, Cut/Copy/Paste (and "Paste as plain text" in rich editors), Select all for text fields, Copy for selected text, Copy link address on links. Nothing to offer → no menu at all (the native one stays suppressed). Shift+right-click opens the native menu in dev only, for Inspect.
- Context menu actions run after the menu closes, with focus back on the right-clicked field. Text inputs use `execCommand`; a contenteditable gets synthetic Ctrl/⌘ key and paste events first, so TipTap runs its own undo, select-all and paste. Paste reads `navigator.clipboard`; if the webview refuses, it logs and does nothing (Ctrl+V still works).
- Document selection menu: flips below the selection when the scroll area has no room above it, and hides once the selection scrolls out of that area (instead of a higher z-index). The menu is absolutely positioned outside the scroll area, so the scroll area is passed as the explicit flip/shift/hide boundary. The document header now sits above the scroll area, not sticky inside it. The menu mounts only once the scroll element exists, because TipTap's React `BubbleMenu` drops the first options update after it registers.
- Plan data: `features/blueprint` and `features/requirements` each have their own `usePlan` (same code, per the "features fetch their own data" rule). It refetches `getPlan` + `planSummary` on `plan:changed` for its project (only the summary when the event's revision is the one we already adopted), adopts the `Plan` a mutation returns, and never adopts an older revision than it holds. Mutations run one at a time through a queue, each sending the last revision seen, so our own quick edits never trip `stale_revision`. On `stale_revision` it refetches and shows "The plan changed elsewhere, so it was reloaded. Try again." with the backend's message under it; that notice auto-dismisses after 8 s, errors stay until dismissed.
- Errors: a refused action shows the backend's message as-is beside the control that caused it (sheet, dialog, requirement row). Canvas actions (connect, delete an edge) have no control nearby, so they use the floating notice at the top of the canvas.
- Blueprint layout (`features/blueprint/lib/layout.ts`) is fully derived from the plan: fixed 60 px rows (Look Across text clamps to 3 lines), 18 px gaps between slice groups, one column per layer. A slice with no requirements gets one empty row slot (no band) for its short box. "Unassigned" is one dashed box in the first column spanning its rows. Each deferred item is a dashed "Later" box one column right of its anchor's layer, so the staircase continues. A requirement whose `sliceId` points at a missing slice counts as unassigned.
- Blueprint canvas: the bands and Look Across column are a single React Flow node at the origin (`zIndex: -1`, `pointer-events: none`, so drags on it pan). Boxes aren't draggable or selectable; React Flow then turns their pointer events off, so the box's own `<button>` sets `pointer-events-auto`. Only edges are selectable. Deleting goes through `onBeforeDelete`, which always returns false: the canvas only ever draws what the plan says, so a refused change leaves it exactly as it was.
- Dependency drag: drag from a box's right dot. While dragging, every other box's target handle grows to cover the whole box, so you can drop anywhere on it. Self, duplicate and non-slice targets are rejected client-side; cycles are left to the backend (its message names the path). The sheet's "Depends on" list (remove / Add dependency) is the keyboard path for the same thing.
- rough.js: one module-level `rough.generator()`, seeded per item with FNV-1a of its id (`lib/rough.ts`), generated paths rendered as SVG under plain DOM text. Shapes are memoized on id + size, so they don't change on re-render, and panning is a CSS transform, so nothing regenerates. Colours come from classes (`stroke-slice`, `fill-slice-fill`), not rough options. New theme tokens `--slice`, `--slice-fill`, `--slice-foreground` (light and dark) in `index.css`.
- Canvas navigation: scrolling pans (it's a tall canvas); Ctrl + scroll or pinch zooms; zoom buttons and Fit to view sit bottom right. Fit to view runs once on first load (`fitView` prop, max 100 %); with ~27 requirements that's about 38 % zoom. React Flow's attribution stays visible: its console asks that it only be hidden by Pro subscribers.
- Status override: the reason dialog opens when moving queued → in progress with any dependency not done (the only move the backend gates). If the backend still answers `dependencies_not_done` (the plan moved underneath), the dialog opens then. queued → done with unfinished dependencies isn't asked about: the backend allows it and wouldn't record a reason.
- Requirements page: Unassigned first, then slices in Blueprint order (layer, then name), including slices with no requirements ("Nothing assigned yet."). Confirm all shows how many it will confirm and is disabled when none. The edit dialog compares fields as typed, sends only changed ones (others `null`), and warns plus relabels Save to "Save as proposed" when a confirmed requirement's text, kind or excerpt changed. The slice menu notes that picking Unassigned on a confirmed requirement moves it back to proposed. The requirements route also shows the Roadmap panel. Its sidebar dot is hardcoded like the others (`bg-[#e0895a]`).
- `PressButton` (`@/shared`): the shadcn `Button` with `usePressScale` built in. Use it for buttons that mount after their parent (inside dialogs, sheets, or only in some states). A `usePressScale` ref on a button that isn't mounted when the hook's effect runs never attaches. Dialog bodies are their own components so they mount with the dialog and start fresh each time.
- Contextual panel switcher, project routes only (decided by the human; the earlier removal above still explains what to avoid): on `/projects/:projectId/*` the panel title is a dropdown between Roadmap (default) and References for that same project. The choice is one session-wide value (`layout/contextual-panel/projectView.ts`), kept across pages and projects and not saved, so a project with no references just shows the References empty state. Teams keeps Agent Chats, Home and Tickets keep no panel, and none of them gets a switcher. This doesn't bring back what made the old switcher messy: a project view only shows where the route names its project, and Agent Chats never shows on a project page. The frame passes the switcher to each project view as its `title`; views draw it in their own header.
- References replaces the planned Bakery canvas: a grid, newest first (reversed `NN` order), with no layout. `bakeryMove` and drop points are never used (`dropPoint: null`), so the cards' `x/y/w/h/z` in `bakery.json` are left as the backend sets them. The Bakery is a per-project store shared by the panel and its pop-out (both can be mounted). Changes run one at a time (a label change renames the file), adopt the returned state, then `bakeryList` again.
- References adding: file drops come from Tauri's `onDragDropEvent` (drag-drop handling is on by default and the window config doesn't turn it off, so HTML5 file drops never reach the webview). A drop counts for a References view only when the topmost element under the pointer (`elementFromPoint`, physical position ÷ `devicePixelRatio`) is inside it, so the pop-out's overlay keeps the panel underneath from also adding. Paste is handled on the view itself (focusable with `tabIndex=-1`), not the window, so pasting an image into the brain-dump editor never adds a reference. Inside a text field, a clipboard holding text pastes the text. Pasted names are reduced to a plain file name (`pasted.png` if empty). There's no file-picker button.
- References editing: fields save on blur or Enter, never per keystroke. Enter also moves focus to the next field in the view (so a fresh batch can be labelled from the keyboard), Escape restores the saved text without saving, and only the changed field is sent (others `null`; tags and applies-to are comma-separated). After a drop or paste in the panel, just that batch shows label + take inline (skip, tags, applies-to behind "More") with the first card's label focused; earlier cards stay compact. The pop-out shows every card's label, take and skip inline. "Needs a note" means no label or no take, the same rule as the backend's `unlabeledCount`.
- References header: the "N need a note" count sits on its own row under the title, inside the header, and only while N > 0. The panel is a fixed 16rem, and beside the icon, the title dropdown and the pop-out button it got cut to "3 need …". The pop-out uses the same header. A fresh card in the panel spans both columns while it's being labelled, so "What do you like about this?" fits; the pop-out keeps every card's "needs a note" line (blank when labelled) so fields line up across a row.
- Settings dialog opening: a layout-level provider (`SettingsDialogProvider` / `useSettingsDialog` in `@/shared`, mounted in `AppLayout` next to the `SettingsDialog` widget), not a URL search param. The dialog is app chrome, not a place: a param would have to survive every in-app navigation, and Back/Forward would open and close it. `openSettings("appearance")` can open a given section; with none, the dialog reopens the section shown last this session.
- Settings saving: one app-wide store (`features/settings/hooks/settingsStore.ts`). Loads and saves run one at a time; each save is `updateSettings({ ...latest, [field]: value })` with `latest` read when the save runs, so two quick changes both land. A control shows its new value while saving; on an error it goes back to the saved value and shows the backend's message under the row as-is. Text and number fields save on blur or Enter; Escape in a changed field puts the saved value back without closing the dialog. Opening the dialog re-reads the settings.
- Theme: the `.dark` class on `<html>` (what `@custom-variant dark` keys off), plus `color-scheme` for native scrollbars. "System" follows `prefers-color-scheme` live. Nothing is cached locally, so until `getSettings` answers the app follows the OS (a user with a non-system theme can see one frame of the other theme at startup).
- Reduced motion: the override feeds the two paths the app already used for the OS setting. A root `MotionConfig` (`AppearanceRoot` in `App.tsx`) sets `reducedMotion="always"` when it's on, else `"user"`, and every `useReducedMotion()` became `useReducedMotionConfig()` so it reads that config. Tailwind's `motion-reduce:` variant is redefined in `index.css` to also match `[data-reduce-motion]` on `<html>`. The add-project dialog's own `MotionConfig reducedMotion="user"` was removed, since it would override the root.
- The settings store lives in each window's webview. There's no `settings:changed` event, so another open window only picks up a change when it next reads settings (its Settings dialog opening, or a restart).
- Folder picker moved from `features/app-sidebar/components/add-project/` to `src/components/folder-picker/` (`FolderBrowser`, `FolderRow`, `LocationChip`) so add-project and Settings can both use it. It still calls `listFolders` itself (the older exception). It has its own `basename` because `components/` doesn't import features. Settings opens it in a second dialog stacked on top (Escape closes just that one).
- Add-project folder: the dialog reads `getSettings` on every open (`features/app-sidebar/hooks/useDefaultProjectsDir.ts`), so a new default applies without a restart. Order: a folder picked in this dialog, then `defaultProjectsDir`, then the last pick in localStorage `foundry:projects-folder`. If `getSettings` fails, it logs and falls back to localStorage.
- Settings fields with no consumer yet (auto-install hooks, verify mode, desktop notifications, severity) carry a `NotActiveTag`. Remove the tag when the feature lands. The AGENTS.md template is read-only text, because no command lists templates.
- Claude Code status in Settings shows only what `claudeStatus` returns: found or not (from `path`), `version`, `loggedIn`, `authMethod` raw, and `problem.message` as-is. `subscriptionType` and `apiProvider` are never shown.
- Corner radii toned down (the human's call, after the rounded menus and dropdowns looked too soft): menu/select popups `rounded-xl`, their items `rounded-md` (concentric with the 6px padding), dialogs `rounded-xl`, input/textarea/select trigger/toggle `rounded-lg`. `button.tsx` is unchanged.
- Modals render inside the window card (supersedes "it also tints the transparent margin" above). `WindowFrame` has a modal layer covering the card (`data-slot="modal-layer"`, `contain: layout`, `overflow-hidden`), and `Dialog`/`Sheet` portal into it via `PortalContainerContext` (`src/lib/portal-container.tsx`). `contain: layout` makes it the containing block for `fixed` children, so overlays fill and blur only the card, and the card's rounded corners clip them. The layer is `pointer-events-none`; its portal children take clicks again. Menus, selects and tooltips still portal to `<body>`, so they sit above the layer and can overhang the card edge like a native popup.
- Settings section registry (supersedes "SettingsDialog widget" in the Settings opening note above): the dialog frame lives in the app layout, `pages/app/layout/settings/` (`SettingsFrame`, `SettingsNav`, and the registry `SETTINGS_SECTIONS` in `sections.tsx`), like the contextual panel's `views.tsx`. Each entry is an id, title, icon, component and keywords; the nav search matches titles and keywords. Each section is a widget: `widgets/settings.tsx` exports one per app-settings section (wrapped in `WithSettings`, which shows loading/error and re-reads settings when the section mounts), plus `widgets/design-library.tsx` and `widgets/role-handbook.tsx`. A new section is one registry entry.
- `useFileDrop` moved from `features/references/hooks/` to `@/shared` (References and the Design Library both use it; about 50 lines would otherwise be duplicated). The "topmost element under the pointer" rule also keeps a drop on the Settings dialog from reaching a References panel underneath it.
- Design Library and Role Handbook are app-wide (no project id). Each feature's hook keeps its own list, runs changes one at a time, adopts the list a change returns, then lists again. Design Library updates send the full patch, with the untouched field read from the latest list when the save runs, so a tag change right after a description edit can't put the old description back. Role Handbook updates send only the changed field (others `null`).
- Saving in the library sheets: tags save as each is added or removed, text fields when they lose focus (Enter in one-line fields, Ctrl/⌘+Enter in textareas), pattern lists when focus leaves the list or a row is removed (empty rows are dropped). Each sheet says so in a muted line at the top and shows "Saving…" / "Saved" under its title. A failed save puts the field back and shows the backend's message under it. "New role" saves nothing until "Add role"; after that, the sheet switches to the new role and saves per field.
- Removing a file or role is done from its sheet ("Remove …" → inline confirm), like deleting a reference. There's no remove action on the list rows.
- Tag suggestions come from `DesignLibrary.families` (every tag in use) minus the file's own tags. Tags aren't lowercased client-side; the backend stores them lowercase.
- Nested overlays: `SheetOverlay` and `DialogOverlay` pass `forceRender`. Base UI skips the backdrop of a dialog opened while another is open (a role or design-file sheet over Settings, the folder picker over Settings), so there was nothing to click to close it and the dialog below wasn't dimmed. Now each stacked layer dims the one below, and clicking that dim closes only the top one.
- Role Handbook drops: `.md` files dropped anywhere on the section go to `roleHandbookAddFromPaths(paths, false)` through the shared `useFileDrop`, with the References "Drop to add" veil, now `DropOverlay` in `@/shared` (both use it). The command returns ids, not the list, so the hook lists again after it whatever the outcome. `role_exists` opens a Replace/Cancel dialog that sends the same paths with `replace: true`; a Replace that fails keeps the dialog open with the message as-is. Every other error shows as-is above the list.
- `role_exists` carries the titles only inside its message ("the Role Handbook already has A, B: replace them, …"). The dialog takes the text between that prefix and the last ": replace them" (so titles with commas or colons survive) and shows the whole backend message instead if the shape ever changes. A structured `titles` field on the error would remove this parsing.
- After a drop, the rows in `added` + `replaced` get a tint that fades after 2.2 s (an absolutely positioned layer, opacity only), the first of them in list order scrolls into view (instant under reduced motion), and a notice says "Added N roles" / "Replaced N roles" / both, dismissing after 6 s.
- Long skill warning: over `LONG_SKILL_WORDS` (1500, in `RoleSheet.tsx`) whitespace-separated words, counted from the text as typed, not only as saved. `RoleField` got a `below(text)` render prop for that.
- `src/components/ui/popover.tsx` added with `shadcn add popover` (Base UI, no new package); its radius changed from `rounded-3xl` to `rounded-xl` to match the other popups. The Format example's text matches `src-tauri/src/features/team/import.rs` (keys, both list styles, title/description fallbacks).
- Setup page (`/projects/:id/setup`, sidebar dot hardcoded `bg-[#8fb87a]` like the others, Roadmap panel): `widgets/setup.tsx` is a vertical stack of sections from `features/setup` (`SetupSection` frame; AGENTS.md now, Team next). The widget's root is keyed by project id, so drafts never carry over to another project.
- AGENTS.md placeholders have no suggested value: `Placeholder.suggestions` is only filled for `designFamily`, and `hint` is guidance ("e.g. Vite / React / TypeScript"), not a value. So textareas start with the confirmed value or empty, and the hint shows muted and as placeholder text. Possible later backend feature: per-placeholder suggestions derived from the roadmap or the project's files.
- Optional placeholders (`optional: true`, including `designFamily`) can be confirmed empty (the backend removes that line), so nothing you don't need blocks Generate. Required ones can't: Confirm is disabled and Enter does nothing while the text is empty.
- There's no unconfirm command. Edit keeps a draft in local state (held by `AgentsMdSection`, not the row, so Generate knows) and counts the placeholder as unconfirmed until Confirm sends it through `confirmPlaceholder`, which replaces the stored value (the backend's `values.insert`). Escape or Cancel drops the draft. A reload mid-edit drops the draft and shows the last confirmed value as confirmed.
- Enter confirms (Shift+Enter for a new line) and focus moves to the next unconfirmed placeholder. In the design-family tag input, Enter adds the typed tag; Enter with nothing typed confirms. The family is sent as `tags.join(", ")`; the backend lowercases, de-duplicates and sorts it.
- A differing AGENTS.md comes back as the error `agents_md_exists` (not a result field). It opens the Replace dialog, which sends `overwrite: true`. The outcome box shows only the result's fields: `agentsMdWritten` ("Wrote AGENTS.md", or that the file already had this exact text), `backup`, `designFamilies`, `copied` (or the "No Design Library file matches…" notice when `designCopySkipped`), `unmatchedFamilies`, `removed`. It's cleared when any value is confirmed again.
- `folder_missing` from any Setup call shows the backend's message once, in a banner at the top of the section, and disables every control until a re-read succeeds (rows and Generate don't repeat it). If it happens on the first load, the section shows only the message and Try again.
- The design-family suggestions come from the Design Library and there's no event for it changing, so the placeholders are re-read when the Settings dialog closes. With no suggestions, the block links to Settings → Design Library (`openSettings("design-library")`).
- `TagEditor` moved from `features/design-library/components/` to `@/shared` (the Design Library and Setup both use it), with an optional `onSubmit` (Enter with nothing typed) and `placeholder`.
- `SetupSection` moved from `features/setup/components/` to `@/shared` (AGENTS.md and Team both use it). The Setup page now owns the scrolling column and stacks two widgets, `Setup` (AGENTS.md) and `TeamComposition` (Team), each keyed by project id inside.
- Team composition state comes only from `getTeam`: null → propose/edit/confirm; a team → the confirmed roster and Add agent. Any `team_confirmed` answer (compose or confirm) shows its message and reads `getTeam` again, which switches to the confirmed view.
- Team proposal is local component state and never saved: a reload, leaving the Setup page or switching project loses an unconfirmed proposal, including a compose still running (the backend run finishes, its result is dropped). The elapsed time is counted locally from the click; there's no cancel and no progress event.
- Propose gating: disabled with "Generate a roadmap first" when `getPlan` has no slices, otherwise with the `planSummary` counts ("Confirm the plan first: N requirements have no slice, …") until `confirmed`. A `planSummary`/`getPlan` error shows as-is as the reason. `features/team-composition` reads both itself and refetches on `plan:changed` for the project.
- Proposal cards: display names compare trimmed and case-insensitively for uniqueness. Empty title → `title: null` (backend uses the role's title). `writeGlobs`/`protectedGlobs`/`avatarBuiltinId` are always sent null, so the backend's defaults (and floor) apply. A related slice id missing from the plan shows the raw id. A card added by hand opens in rename mode with its name selected. Discarding a proposal asks first (it was a paid run).
- Custom roles need only a title client-side; description and skill text may be empty (trimmed). The backend's own rules apply at confirm/add.
- Avatars: proposal cards always show `/pfp.png` (a feature-local `DEFAULT_AVATAR`; the roadmap's copy can't be imported). Confirmed agents use `agentAvatar` once per agent id, refetched only after a successful `setAgentAvatar`; null or an error shows `/pfp.png` (errors are logged, not shown). Built-in avatars have no image source in the bindings, so the picker shows them as buttons labelled by id.
- Avatar upload is paste-only (on the popover, which focuses its paste target on open). Dropping a file can't work: Tauri delivers drops as paths and `setAgentAvatar` only takes bytes, with no path variant (unlike `bakeryAddFromPaths`). Needs a backend `bytes`-from-path option or an `AvatarChoice.path`.
