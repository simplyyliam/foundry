# Frontend decisions

Append one line per decision that isn't obvious from the code. Newest at the bottom.

- Backend contract: `appInfo()` is called on mount in `App.tsx`. `app:ready` is best-effort (it can fire before the webview listens), so don't rely on it.
- Projects: a project row in the sidebar only expands and collapses its sub-items; it doesn't navigate. The sub-items are `PROJECT_SECTIONS` in `src/features/projects/model/project.ts` (Idea → `/projects/:id/idea`, which renders the `Document` widget; Blueprint → `/projects/:id/blueprints`, still a placeholder). `/projects/:id` redirects to the first section. To add a sub-page, add an entry there and a page at `src/pages/app/projects/[projectId]/<segment>/page.tsx`.
- Archiving the open project closes it: the frontend navigates to Home itself after `archiveProject` succeeds. If the backend returns `session_running` (or any error), show its message and do nothing else.
- Delete exists only for archived projects and requires typing the project name. `deleteRepository` moves the folder to the Recycle Bin. It's the one project mutation that doesn't refresh the list itself: the dialog refreshes after its close animation, because the row (and the dialog inside it) would otherwise vanish mid-animation.
- Add-project dialog: a folder that belongs to an archived project is offered as "Archived · restore", and picking it unarchives and opens it.
- Folder picking is a custom in-app browser (`listFolders` / `folderLocations`), not the native OS dialog: the native one can't be styled. Prefer styleable in-app UI over native dialogs.
- Add-project dialog is one view: a search field, a folder button that picks where projects live (remembered in localStorage `foundry:projects-folder`), and that folder's subfolders listed below with no background. Typing a name that matches no folder offers "Create “name”" at the top. An earlier two-option design ("New repository" / "Link existing folder") was rejected; don't bring it back.
- No client-side project-name validation: `createRepository`'s own rules and messages apply (it answers `invalid_input` / `folder_exists`).
- Dialogs use the shadcn `Dialog` (`src/components/ui/dialog.tsx`), not a custom modal. Its overlay is `fixed inset-0`, so it also tints the transparent margin around the frameless window. That's known and left as is for now.
- Sidebar look (from the design): project rows and sub-items use 12px text; sub-items are a colored dot plus label with no guide line; the "Archived" group sits above "Projects", is collapsed by default and shows its count in a shadcn `Badge`. The Projects "+" is hidden until the Projects header row (only that row) is hovered or focused; the chevron then slides left to make room.
- Older code that predates the shadcn/theme-token rule: plain `<button>`/`<input>` in the add-project dialog, `ProjectNameEditor` and `ProjectsGroup`; hardcoded colors for the sidebar logo square (`bg-red-400`), the sub-item dots (`PROJECT_SECTIONS`) and the roadmap boxes (`bg-black/[0.055]`).
- Contextual panel: views come only from the route. Idea and Blueprints → Roadmap; `/teams` → Agent Chats; `/tickets` → a reserved "tickets" view (`component: null` until the ticket system exists); Home → no panel yet (undecided). A manual dropdown switcher was built and then removed: one project's Roadmap from Teams, or Agent Chats from a project page, got messy. On routes with no view the panel unmounts (no slide animation).
- Roadmap avatar: the Product Lead's avatar can't be displayed yet. The asset protocol scope is empty and built-in avatars have no images, so it falls back to `/pfp.png` (also for no team, no Product Lead, or an error). A backend fix is coming separately.
- Roadmap generation state lives in a store keyed by project id (`features/roadmap/hooks/useGeneration.ts`), and `roadmap:progress` is listened to from app start (`AppLayout`), so switching views or pages mid-run doesn't lose it. After a full reload a run is only seen again at its next stage event; Generate meanwhile returns `generation_running`, shown as-is. The elapsed time counts up locally from the last event's `elapsedMs`.
- Roadmap load: after `generateRoadmap` succeeds, the plan is re-read and that fresh revision goes to `loadRoadmap`, instead of the revision from the click. That way an edit during a minutes-long run doesn't force another paid generation. If more requirements got confirmed during the run than the user agreed to discard, ask again with the new count before loading.
- Roadmap highlighting of uncovered paragraphs in the editor is deferred until a document editor exists. `features/document` is still empty; the "Needs a look" box lists the uncovered paragraphs meanwhile.
- Document editor: TipTap 3 with the official `@tiptap/markdown` (not the older community `tiptap-markdown`). The editor loads markdown and saves markdown; nothing else is stored. `@tiptap/pm` is listed explicitly because it's TipTap's required peer and the highlight plugin imports it. Underline is turned off (markdown can't hold it), links don't open on click (it would navigate the webview), and a bare `example.org` typed in the link field becomes `https://example.org`.
- Document saving keeps untouched blocks byte for byte (`features/document/lib/markdown-source.ts`): each top-level block is tied to its source text, verified by parsing that text alone and comparing (`eq`). A block that is the same node, or equal to a block from the loaded file (Enter at a paragraph's end, undo), is copied from the source; only edited blocks go through the serializer, which would otherwise rewrite the whole file (`_a_` → `*a*`, `\[x\]`, `&lt;`). Line endings (CRLF) are kept. Empty paragraphs are never written.
- Document autosave: 800 ms after the last edit, plus on blur, unmount (leaving the page or switching project; the widget is keyed by project) and window close. Saves run one at a time in order, and a load waits for every queued save, so the old project's edit lands before the new project loads. A save whose text equals what's on disk (or already queued) is skipped, so opening without editing never writes. Text whose save failed is kept in memory per project and shown again (and retried) on the next visit.
- Window close: the capabilities don't grant `core:window:allow-destroy`, so Tauri's `onCloseRequested` helper (which calls `destroy()`) would leave the window stuck. The document prevents the close, saves, removes its listener and calls `close()` again. If that save fails, the window stays open once with the error showing; closing again closes.
- The save status ("Saving…", "Saved", or the backend's message as-is) sits in the document's own sticky header row at the top right, not in the breadcrumb header. Nothing shows until the first edit.
- Uncovered-paragraph highlighting (supersedes the "deferred" note above): `features/document` reads `getRoadmap` itself and refetches on `roadmap:progress` `done`. A top-level block is highlighted only when its saved text, whitespace-normalized like the backend's `normalize_ws`, equals an uncovered paragraph and it hasn't been edited since; it's a ProseMirror node decoration, so the document never changes. A backend paragraph spanning several blocks (no blank line between them) is never highlighted.
- Known parser limit: `@tiptap/markdown` drops inline HTML (`a <div> tag` shows as `a  tag`). Untouched paragraphs keep it in the file; editing that paragraph removes the tag from the saved text.
- Known gap: the Roadmap panel reads `getDocument` for "No brain dump yet" only when it mounts. There's no document-changed event, so after typing the first text it keeps saying the brain dump is empty until it remounts. Not worked around (it needs a backend event, or another rule).
- Context menu: one app-wide shadcn `ContextMenu` (`AppContextMenu` in `@/shared`, mounted in `App.tsx`) replaces the webview's native menu everywhere, portals included. Its items are built at right-click time from what was clicked: groups registered with `useContextMenu(ref, provider)` (innermost region first), then built-in Undo/Redo, Cut/Copy/Paste (and "Paste as plain text" in rich editors), Select all for text fields, Copy for selected text, Copy link address on links. Nothing to offer → no menu at all (the native one stays suppressed). Shift+right-click opens the native menu in dev only, for Inspect.
- Context menu actions run after the menu closes, with focus back on the right-clicked field. Text inputs use `execCommand`; a contenteditable gets synthetic Ctrl/⌘ key and paste events first, so TipTap runs its own undo, select-all and paste. Paste reads `navigator.clipboard`; if the webview refuses, it logs and does nothing (Ctrl+V still works).
- Document selection menu: flips below the selection when the scroll area has no room above it, and hides once the selection scrolls out of that area (instead of a higher z-index). The menu is absolutely positioned outside the scroll area, so the scroll area is passed as the explicit flip/shift/hide boundary. The document header now sits above the scroll area, not sticky inside it. The menu mounts only once the scroll element exists, because TipTap's React `BubbleMenu` drops the first options update after it registers.
